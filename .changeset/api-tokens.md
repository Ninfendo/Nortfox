API tokens and scopes, the fourth part of login: a member makes a token for a program, and the program calls `/v1` with it. `docs/api.md` gives the rules, under Who acts, Scopes and The API tokens.

- `createApiToken` makes an API token for the company the session works in, with a name of 1 to 100 characters on one line and one or more scopes. Its answer, `NewApiToken`, shows the token once, `nft_` and 43 characters, and the server keeps only its hash. Only a browser session makes a token: a token gets 403 `session-required`, so a token never makes a token. A repeat with the write's idempotency key gets 409 `answer-shown-once`, with the rest of the first answer in `answer`, the token's id among it, and makes no second token.
- A program sends the token as `Authorization: Bearer <token>`, on `/v1` only: `/mcp` never takes it. A request with a bearer token ignores the session cookie. The token acts as the person who made it, with the actor kind `integration`, in its one company. It may do what its scopes and its person's permissions there both allow, read on every request, so a right the person loses, also by the end of a Revisor grant, is refused from the token's next request.
- A token stays in its company. Through a token, `getMe` gives no personnummer and no mobile number, `listCompanies` gives the token's company alone, and an operation that names another company in its input gets 422 `company-not-available`, as for a company that does not exist. `createCompany` is the one operation that reaches outside: it makes the person a new company. Its idempotency key through a token is the token's own, so a key that the person's browser used gets 422 `idempotency-key-reused` and never the browser's company. An operation that runs before sign-in takes a token's call as a call with no actor, so a token links nothing to an invitation.
- `listApiTokens` lists the company's live tokens, `ApiToken`, never the token itself: a member's own, or every one of the company for a system administrator. `revokeApiToken` revokes one, the member's own or, for a system administrator, any of the company's, and it is refused from the next request on. Any other id gets 422 `api-token-not-found`.
- A token works until it is revoked. While its member is deactivated it is refused, and it works again once the member is active again. A removal, a leave and a disconnect revoke the member's tokens.
- Each operation that a token may call names a scope, one of `SCOPES`: `companyinformation` for `getCompany` and `profile` for `getMe`, as in the established API, and NortFox's own `companies`, `users` and `tokens`; the list also holds the established API's names that later slices use. A name is case-sensitive, and `createApiToken` refuses any other name, also one that differs only in letter case. A token without the operation's scope gets 403 `scope-missing`, which names the scope in `scope`, also when its person holds the permission. A browser session is not limited by scopes.
- A token is refused `getSession`, `selectCompany` and `logout` with 403 `session-required`. `listRecentCompanies` now needs a browser session too, since it tells about the person's other companies.
- Every member now holds `tokens:own`, and a system administrator `tokens:all`, so `getMe` lists them. A session takes its permissions when it chooses its company, so a session that chose it before this release gets `tokens:own` when it chooses the company again or signs in again.
- The behandlingshistorik names, for each change through a token, the token beside the person and the kind `integration`, and the database refuses an integration's write that names no token or client. Each token made and revoked is an entry: Program "Användare", Rubrik "API-token skapad" or "API-token återkallad", with the token's id, name and scopes.
- `openapi.json` gives each operation's scope, `x-nortfox.scope`, the fields of its answer that hold a secret, `x-nortfox.secretOutput`, and the session mark `only` for an operation that needs a browser session. It names the bearer token as the security scheme `bearer` beside `sessionCookie` on each operation that names a scope, and the 401 of such an operation gives both challenges, `Cookie` and `Bearer realm="NortFox"`. A refusal of a request with a bearer token names RFC 6750's error code: a 401 to a token that names no actor gives `Bearer realm="NortFox", error="invalid_token"`, the same for every such token, and a 403 to a token gives `WWW-Authenticate: Bearer realm="NortFox", error="insufficient_scope"`, with `scope="<scope>"` for `scope-missing`. Each 403 says when a token gets `session-required` or `scope-missing`. The TOTP enrolment's `otpauth` URI and the sign-in's challenge are marked as secrets.
- The client takes the option `token`, which it sends as `Authorization: Bearer` with every call, has `createApiToken()`, `listApiTokens()` and `revokeApiToken()`, exports `ApiToken`, `NewApiToken` and `Scope`, and gives `scope` and `answer` on a problem. Each method's doc comment names its scope, says when it needs a browser session, and names the secrets of its answer.
