# 9. Company isolation and database roles

Status: accepted, 2026-11-01. Amended 2026-11-03, in slice 2a: no company table keeps planner statistics or has a partial index, a key of one column holds only random ids or ids that order the changes, no role of ours reads the locks that other backends hold, and a reader can still set its own role settings, its password and its default privileges. Amended 2026-11-04, in slice 2c: the install-wide tables of the schema `access`, with their classes, and the lookup functions; and the memberships, a company table in `access`, with the one function that reads a person's memberships across companies, and the only ways a request enters a company. Amended 2026-11-09, in slice 2c: the people of a company, one more function that reads the memberships as the owner, only in the transaction's company.

## Context

One NortFox install holds many companies, for example all the clients of an accounting firm. A bug in a query must never show one company's books to another. The server should have no more rights than it needs.

## Decision

- Every table with company data has a `company_id` column, row level security that is enabled and FORCED, and a policy that matches `company_id` to the company for the transaction.
- For the app role, the company for the transaction is a setting. The server sets the company and the actor with `SET LOCAL` at the start of each transaction, so a pooled connection never carries them over.
- Tables that do not belong to one company, such as the login identities, are install-wide tables in the schema `access`. Each has one of four classes, which sets its policies: a person's own rows, by the person the transaction acts as; rows of one company, by the transaction's company; rows any request may read; or secret rows, which the app reaches only through lookup functions ([db/README.md](../../db/README.md#the-schema-access)).
- The database roles:
  - **owner** owns the schema and runs the migrations. The server never uses it. Only the owner role records a void range in a voucher series ([decision 2](0002-ledger-law-in-postgresql.md)).
  - **app** is the server's role. It reads and writes rows, nothing more. It cannot change the schema, disable a trigger or bypass row level security.
  - **reader** roles can only read. Each reader role is bound to one company in a table that only the owner role writes, and its policies compare `company_id` with that table for `current_user`. A reader's policies never trust a setting, because any role can change a setting.
- Outside tools use the API, with a token bound to one company. A reader role is only for a tool that must read the database directly.
- No role used at runtime is a superuser or has `BYPASSRLS`.

## Consequences

- A query without a company set returns nothing. It never returns everything.
- A reader role that sets another company's id still sees only its own company.
- No company table keeps planner statistics of its values. Otherwise a reader's `EXPLAIN` would show from its row estimates the values of another company's rows. The planner then uses its default estimates, which can give a worse plan for a large report. PostgreSQL cannot hide the totals: every role sees how many rows each table holds over all the companies of the install ([db/README.md](../../db/README.md)). No company table has a partial index, whose row count every role would see too, counting the rows of every company that meet its condition.
- A reader's `EXPLAIN ANALYZE` shows real counts, of rows and of pages. So a reader's policy reads its company once for the whole query, before any row: otherwise the planner would check the reader's own conditions first, and the count would show how many of another company's rows meet them. A key of one column, such as a primary key, leaves `company_id` out. After a lookup by it, `EXPLAIN ANALYZE` counts the rows that the policy removes, so a reader learns whether another company's row holds an id, and how many such rows fall in a range of ids. So each such id is random, or only orders the changes, as the history's does, and never carries a time or a value ([db/README.md](../../db/README.md)).
- No role of ours reads `pg_locks`, the owner neither. Each company's transactions take the company's turn, an advisory lock on the hash of its id, and `pg_locks` would show that lock to every role: when each other company books or changes its locks, and, by the transaction's id, whether each change committed. PostgreSQL cannot hide the rest: every role sees in `pg_stat_activity` when the install's transactions run, with their ids, and `pg_xact_status()` tells whether each committed, over all the companies ([db/README.md](../../db/README.md)).
- A reader, like any role, can still set its own role settings and its password, which the cluster's catalog keeps, and its own default privileges, which the database's catalog keeps. PostgreSQL has no privilege to stop it. A superuser sees them and clears them, and runs `DROP OWNED BY` before it drops a reader ([db/README.md](../../db/README.md)).
- Work that spans companies, such as the doctor's checks, runs company by company.
- A secret install-wide table, such as the password hashes and the sessions, has no policy and no privilege for the app. The app reaches its rows only through the lookup functions, each owned by the owner, `SECURITY DEFINER` and with its `search_path` pinned. Each takes a hash or an identifier and gives the one row its caller needs. So no query of the app can list the sessions, the hashes or the sealed TOTP secrets.
- The memberships, a person in a company, are a company table in the schema `access`, with the company policies like any other. A reader reads its company's memberships there, and nothing of an install-wide table. Which companies a person may enter is the one question that crosses companies, so one function answers it, `access.active_membership`, which reads the person from the transaction's actor, never from a parameter. It reads through a policy of the owner's by person, on the memberships and on the companies, which no other function the app may run reads through. In the server one module calls it, and a request's company is made only from that module's answer. A guard keeps every other file of the server from the function, the memberships and the objects the module makes, and from the transaction's settings: only the database layer sets them, and a transaction in a company takes its company only as a company access that the module made, for its actor. A request that starts in no company, such as a session's lookup or a person's own request about one of their companies, sets a company only from an answer that the function gave in the same transaction, for the person that transaction acts as. A session keeps the membership it chose a company with. The database ends the session when that membership stops being active, and the server asks the function again on every request, so the session ends at its next request once that membership is no longer the person's active one. The one other way into a company is to make it: the database layer picks the new company's id itself, so no caller can name an existing company there. A later slice adds grants through an accounting firm inside that function, and row level security stays as it is. A company has an active system administrator from its first commit, which a check at each commit keeps ([db/README.md](../../db/README.md#the-schema-access)).
- The names and e-mail addresses of a company's people come from one more function, `access.company_people`. It reads the memberships as the owner, since the app may not read another person's identity, but only in the transaction's company, and it gives no personnummer and no mobile number. The catalog test pins its whole definition, so a change to what it reads counts like any other function that reads the memberships ([db/README.md](../../db/README.md#the-schema-access)).
- The table guard checks each install-wide table against its class, from the catalog, as it checks each company table, and fails a table in `access` that is on neither list.
- Tests run as the app role and as a reader role against real PostgreSQL. A guard fails if a table lacks FORCE RLS or its policy.
